# Project Planner

This skill walks the user through creating a **complete, consistent set of project planning documents** for any software project. The result is a `docs/` folder with up to 5 files, each following a strict, reusable structure.

The documents are generated **in a fixed order** because each one builds on the previous. You cannot write TASKS.md without the PRD. You cannot write the DEPENDENCY_TREE without TASKS.md.

**Your role:** Interview the user, then generate each document one at a time. Wait for the user to approve or revise each one before moving to the next. Each document is generated by reading its reference file for the exact structure — don't improvise the format.

---

## Document Order & Applicability

Generate documents in this exact sequence. Skip documents 2 and 3 if the project has no frontend. Skip document 5 unless the user explicitly requests it:

| # | File | Generate by default? | Reference |
|---|------|---------------------|-----------|
| 1 | `docs/PRD.md` | ✅ Always | `references/prd-structure.md` |

## Workflow

### Step 0 — Intake Interview

Before writing anything, conduct a structured intake. Ask **all of these questions in one message** (not one at a time):

1. **What does the project do?** (2–3 sentence description)
2. **Who are the users and what roles do they have?** (single user, admin/user split, public-facing, etc.)
3. **What is the tech stack?** (frontend framework, backend language, database, auth provider, AI services, etc.) — If the user isn't sure, help them decide.
4. **Does it have a frontend?** (yes → generate docs 2 and 3; no → skip them)
5. **What are the core features?** (bullet list — don't worry about ordering yet)
6. **Are there any custom algorithms or scoring systems?** (e.g., ranking, matching, calculation)
7. **Any future features that are explicitly OUT OF SCOPE for V1?**

Optionally ask (if the project has a frontend):
8. **What is the visual direction?** (dark/light, color palette, brand feel, any reference apps)

Don't proceed until you have answers to questions 1–5 at minimum. Questions 6–8 can be skipped if not applicable.

---

### Step 1 — PRD

**Before writing:** Read `references/prd-structure.md` in full.

Generate `docs/PRD.md` following the structure exactly. The PRD should be comprehensive — it is the foundation for everything else. Include:
- All features from the intake, fully fleshed out
- Data models (all tables with all columns)
- API endpoints (high-level)
- Scoring algorithm if applicable (full pseudocode)
- UI overview (layout + key screens table)

After generating, present it to the user and say: *"Here is the PRD. Review it and let me know if anything is missing, incorrect, or needs expanding. Once you approve it, I'll move to the [next step]."*

Do not move to Step 2 until the user explicitly approves the PRD (or says "looks good", "continue", "next", etc.).

---

### Step 2 — design.md (Frontend projects only)

**Skip this step entirely if the project has no frontend.**

**Before writing:** Read `references/design-structure.md` in full.

Generate `docs/design.md` with the YAML token block followed by the markdown guidelines. Use the visual direction the user described in the intake (Step 0, question 8). If they didn't specify, make reasonable creative decisions based on the product type and brand tone, but call out your choices explicitly so the user can adjust them.

After generating, present it and say: *"Here is the design system document. The YAML block contains all your design tokens. The markdown section explains how to use them. Review and let me know any adjustments."*

Do not move to Step 3 until approved.

---

### Step 3 — FRONTEND_DESIGN_SPEC.md (Frontend projects only)

**Skip this step entirely if the project has no frontend.**

**Before writing:** Read `references/frontend-spec-structure.md` in full.

Generate `docs/FRONTEND_DESIGN_SPEC.md`. Derive every screen from the PRD's UI Overview section (Section 9). Every screen listed there must have an entry here. For each screen, enumerate every interactive element and data display area the PRD describes.

After generating, present it and say: *"Here is the frontend component spec. It enumerates every element that must appear on each screen. Review it and flag any missing components or screens."*

Do not move to Step 4 until approved.

---

### Step 4 — TASKS.md

**Before writing:** Read `references/tasks-structure.md` in full.

Generate `docs/TASKS.md` from the approved PRD (and design docs if applicable). The phases must:
- Start at Phase 0 (scaffolding) and end with a polish/UX phase
- Deliver vertical slices (testable outcomes, not just backend OR frontend)
- Follow the correct dependency order (no phase references work from a later phase)
- Cover every feature in the PRD

After generating, present it and say: *"Here is the full task breakdown. Each phase is a vertical slice. Review the phases, goal statements, and verification checkpoints. Let me know if any feature is missing or any phase seems too large/small."*

Do not move to Step 5 until approved.

---

### Step 5 — DEPENDENCY_TREE.md (Opt-in only)

**Skip this step by default.** Only generate `docs/DEPENDENCY_TREE.md` if the user has explicitly asked for it — either during the intake interview or at any point before Step 5.

If the user has not asked for it, complete the wizard at Step 4 and move to Step 6 (Completion) directly.

If the user did explicitly request it:

**Before writing:** Read `references/dependency-tree-structure.md` in full.

Generate `docs/DEPENDENCY_TREE.md` from the approved TASKS.md. The dependency tree is derived mechanically from TASKS.md — every phase already has implicit dependencies from the vertical slice design. Map them out explicitly.

After generating, present it and say: *"Here is the dependency tree. It maps every phase to its prerequisites, shows the critical path, and identifies all parallel work opportunities. Review the critical path and parallel windows — this is what determines minimum project time."*

---

### Step 6 — Completion

Once all applicable documents are generated and approved, confirm to the user:

```
✅ Planning complete. Your docs/ folder contains:
- PRD.md                  — Product requirements, data models, API surface
- design.md               — Design tokens and visual guidelines  (if frontend)
- FRONTEND_DESIGN_SPEC.md — Component inventory per screen (if frontend)
- TASKS.md                — Phased implementation checklist with intra-phase ordering
- DEPENDENCY_TREE.md      — Phase dependencies and critical path (if requested)

Start with Phase 0 in TASKS.md.
```

## General Rules

- **Never skip reading a reference file** before generating the corresponding document. The reference defines the format — you cannot know it from memory alone.
- **Never generate two documents in the same message.** One document → user review → next document.
- **Never deviate from the reference structure** — section order, header formats, required fields, and static blocks are non-negotiable.
- **Never pre-fill tasks as checked** — all checkboxes in TASKS.md start as `- [ ]`.
- **Write to `docs/`** — all files live in a `docs/` folder at the project root unless the user specifies otherwise.
- **Ask before skipping** — if you're unsure whether a section applies (e.g., "does this project need a scoring algorithm section in the PRD?"), include it with a brief note rather than omitting it silently.
- **Stay in the wizard** — between steps, always remind the user what step you just completed and what comes next.
